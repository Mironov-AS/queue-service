## 5. Процедура переключения (после согласования)

### Этап 1 — серверный код, внешний вид не меняется

```bash
bash /opt/queue-service/releases/2026-10-30-booking/prod-switch.sh
```

Скрипт: снимает согласованный снимок базы → сохраняет резервную копию кода →
останавливает службу → копирует новые файлы и недостающие модули `node_modules`
(`pg` и его зависимости; существующие модули не трогаются) → запускает службу →
проверяет `/health`, `/api/queue`, `/visitor` → при любой ошибке **сам** откатывает
код из резервной копии и поднимает службу обратно.

### Этап 2 — клиент с интерфейсом записи и включение модуля

```bash
bash /opt/queue-service/releases/2026-10-30-booking/prod-switch.sh --with-client
```

Дополнительно: в `/etc/systemd/system/queue-service.service` добавить строку
`EnvironmentFile=/opt/queue-service/secrets/booking.env` (файл уже создан и содержит
`BOOKING_ENABLED=true` и `BOOKING_DATABASE_URL`), выполнить `systemctl daemon-reload`.
После этого `/api/booking` перестаёт отдавать 503 и появляются вкладка «Запись»
и справочник услуг с переключателями каналов.

### Этап 3 — включение канала «Запись» у услуги

В панели администратора: шестерёнка → «Услуги» → «Редактировать» → вкладка «Запись»:
длительность, количество постов, часовой пояс, рабочие дни и время, поля клиента.
После сохранения появляется постоянная ссылка и код для iframe.

## 6. Что происходит с данными

- **Очередь не переезжает.** База `queue.db` остаётся на месте, в переключении она только
  читается (снимок) — история талонов, номера, настройки и рекламные файлы не меняются.
- **Запись живёт отдельно** в PostgreSQL (`queue_booking`). Даже если её отключить,
  сделанные записи остаются в базе.
- **Откат.** Резервная копия кода + снимок базы позволяют вернуть прежнее состояние
  за десятки секунд. Важно: если после включения записи клиенты уже записались,
  возврат на старую версию без обратной переноса этих записей их не сохранит —
  поэтому откат применяется только на этапе 1, до включения записи.

## 7. Проверки после переключения

```bash
systemctl is-active queue-service
curl -s http://127.0.0.1:3001/health
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3001/visitor
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3001/api/booking/services   # 401 без токена

```

## Исследование переключения каталогов
На временных файлах песочницы проверена модель атомарной смены символьной ссылки: отказ предварительной проверки оставляет старую версию; при моделируемом отказе после переключения ссылка возвращается; внешние тестовые данные и медиа не меняются. Это только модель файловых операций, не проверка systemd, базы данных или production-отката. Существующая служба использует реальный каталог `/opt/queue-service/server`, а не ссылку; для перехода нужна отдельная проверенная процедура. При анализе обнаружено: действующий `storage.js` использует `/opt/queue-data/uploads` (0 файлов), тогда как `/opt/queue-service/server/uploads` содержит 2 файла; нельзя без проверки считать последние используемыми либо удалять их. Старый скрипт переключения остаётся запрещён.

Проверка синхронизации: ошибка чтения справочника очереди больше не трактуется как пустой справочник, чтобы не деактивировать услуги записи; проверено тестом с имитацией ошибки и изолированным PostgreSQL (4/4). В старый локальный prod-switch.sh добавлена безусловная защитная остановка: он не выполняет никаких действий, пока не заменён безопасной испытанной процедурой. Кандидат на ВМ не обновлён этим изменением; промышленная выкатка по-прежнему не выполнена.

Последняя репетиция: собран актуальный клиент, отдельный кандидат `/opt/queue-service/releases/booking-final-preflight-20261030/server` содержит клиент с HTTPS-кодом встраивания и исправленный bookingIntegration. На отдельном порту, копии ранее созданного снимка и временной PostgreSQL прошли 18 проверок API, включая обе отметки, переполнение и отмену. Действующую службу не останавливали. Важно: процесс переключения и отката всё ещё не испытан, реальная вёрстка iframe и админка в браузере не проверены; это не разрешение на выкатку. При проверке загрузки модуля без DATA_DIR создана отдельная пустая база в домашнем каталоге пользователя root на ВМ; промышленная база не использовалась.

Испытана новая экспериментальная модель переключения `deploy/switch-engine.sh` в временном каталоге с имитацией управления службой: ошибки валидации, создания снимка, остановки, контроль после переключения и успешный путь; данные в тесте сохранены, промышленный путь отклоняется защитой. Это не systemd-испытание и не рабочий production deploy: скрипт предназначен исключительно для изоляции. Полный набор серверных тестов с изолированной PostgreSQL: 63/63. Промышленную службу не переключали.

На ВМ выполнено изолированное испытание модели переключения с настоящим временным systemd-сервисом и отдельным портом: искусственный сбой проверки новой версии вернул старую, затем успешное переключение показало новую; тестовый файл данных не изменился. Временный сервис и каталог удалены; промышленный сервис не останавливался и отвечает. Это испытание модели, не готовая процедура выкатки: тест использует простой сервер и тестовый файл вместо настоящего приложения и БД; действующий prod-switch.sh остаётся заблокирован.

При проверке изолированного механизма найден и исправлен частичный сбой остановки: служба могла остановиться, хотя команда stop вернула ошибку, до установки фазы отката. Фаза восстановления теперь устанавливается до stop. Тесты моделируют такую ошибку и проверяют запуск старой версии и сохранность данных. Повторена репетиция реального приложения с отдельной PostgreSQL и 18 smoke-проверками; production-путь по-прежнему блокируется, это не промышленный адаптер.

Дополнительная проверка systemd: действующая служба требует существования `/opt/queue-service/server/uploads` через `ReadWritePaths`. В кандидате этого каталога нет. На отдельной временной systemd-службе подтверждено: при отсутствии разрешённого пути запуск завершается кодом 226, при наличии каталога succeeds. При будущей подготовке production-кандидата обязательно сохранить дерево старого `server/uploads` (в нём два файла в `ads/`) и права владельца; не удалять старую копию. Текущий код фактически читает uploads из `DATA_DIR`, но это не отменяет требования systemd и необходимость сохранения существующих файлов. Промышленная служба не перезапускалась, API очереди ответил 200.

В изолированной репетиции дерево legacy uploads скопировано вместе с владельцем и правами; содержимое сверено. Тестовая служба запущена под queueapp с ProtectSystem=full и отдельными ReadWritePaths, включая каталог uploads; отказ, откат, переключение и 18 проверок записи прошли. Для расположенного в /tmp тестового каталога PrivateTmp=false (с PrivateTmp=true каталог скрыт и был получен 226/NAMESPACE), поэтому репетиция не воспроизводит PrivateTmp=true production в точности. На production изменений нет; финальный switch остаётся заблокирован.

Проведена новая изолированная репетиция вне /tmp, с PrivateTmp=true, ProtectSystem=full, NoNewPrivileges=true и запуском от queueapp. Сохранена копия legacy uploads; при принудительном сбое выполнен откат, затем переключён кандидат и пройдены 18 smoke-проверок записи. Это испытание тестового механизма, не готовый production-адаптер: промышленный скрипт остаётся заблокирован.
