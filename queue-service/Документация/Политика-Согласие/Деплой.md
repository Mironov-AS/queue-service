## Почему деплой безопасен для очереди и данных
- Изменён только фронтенд (новые React-страницы + ссылки). Миграций БД нет,
  схема `queue.db` не меняется, API `/api/*` не меняется.
- `server/public` в проде обновляется из `client/dist` на старте контейнера;
  том `queue_data` (`/app/server/data`, где живёт `queue.db`) при пересборке
  образа не пересоздаётся. `entrypoint.sh` перед стартом делает ротационный
  бэкап `queue.db.bak.1..3` и только потом запускает сервер (миграции — additive).
- Маршруты SPA (`/privacy`, `/consent`) обслуживаются существующим fallback
  `app.get("*") → index.html` в `server/index.js`, новых nginx-правил не нужно.

## План деплоя (выполнять, когда будете готовы)
1. Бэкап: скопировать текущий прод-`queue.db` (плюс `queue.db-wal/shm`)
   из тома `queue_data` в отдельную папку вне тома. Проверить размер/дату.
2. Убедиться, что реквизиты вставлены и тексты на экране совпадают с Word-версиями.
3. Собрать образ штатным способом (`docker compose build`) — фронт соберётся
   внутри `frontend-builder`, серверные зависимости ставятся заново.
4. Остановить и поднять сервис (`docker compose up -d`): простой — секунды,
   пока контейнер пересоздаётся; очередь и данные лежат в томе и переживают
   пересоздание. Проверить лог `entrypoint.sh`: «Backup saved», `[db] schema version`.
5. Проверки после подъёма:
   - `GET /health` → 200;
   - `/visitor` открывается, виден текст согласия и ссылки;
   - `/privacy` и `/consent` открываются, тексты совпадают с Word;
   - `/terminal` — тот же текст согласия;
   - взять тестовый талон и отменить его, очередь обновляется;
   - общий экран (`/dashboard`) по-прежнему без ФИО/телефонов/номеров авто.
6. Откат: остановить контейнер, вернуть сохранённый `queue.db*` в том
   (при этом деплое отката БД не потребуется — схема не менялась),
   поднять предыдущий образ.
