# Предварительная запись — разработка в песочнице

## Цель и ограничения
Единый справочник услуг с независимыми каналами очереди и предварительной записи. Очередь не резервирует посты: администратор направляет клиентов вручную. Посты ограничивают одновременные предварительные записи одной услуги. График, исключения, данные формы, календарь и постоянный виджет на услугу. Услуги, уже существующие в очереди, сохраняют прежнее поведение. Отдельное согласие и политика для записи требуют проверки применимости, версии текста и фиксации факта согласия.

## Архитектура
Существующий фронтенд: React/Vite; сервер: Express/Node.js. Целевая постоянная база: внешняя PostgreSQL через DATABASE_URL, без SQLite fallback. Текущий исходный сервер всё ещё использует SQLite: миграция на PostgreSQL и перенос данных ещё не выполнены. Настоящие production-данные для тестов не используются.

## Статус
Начата реализация независимого расчёта слотов и тестов. Админка, виджет, сохранение, блокировка конкурентных записей и миграция не реализованы. Промышленный сервер нельзя изменять до отдельной явной команды пользователя. На окончательном переключении требуется безопасная копия, репетиция, проверка целостности и согласованное окно с планом отката.

## Локальная проверка
Тесты логики: `node --test server/tests/booking-slots.test.js` из корня проекта. Для запуска полного приложения в будущем потребуется отдельная PostgreSQL и DATABASE_URL; подключение к промышленной БД запрещено без отдельного согласования.

## Продолжение — серверная основа
Добавлены зависимость `pg`, проект схемы PostgreSQL для настроек записи и бронирований и отдельный репозиторий. Предусмотрены постоянный идентификатор виджета, блокировка строки конфигурации при бронировании, проверка вместимости и сохранение снимка введённых полей и текста согласия. Схема намеренно не запускается автоматически: она зависит от мигрированной таблицы услуг PostgreSQL. Тесты `node --test server/tests/*.test.js` выполняют 8 модульных проверок; mock базы в одном тесте не является проверкой PostgreSQL или конкурентного бронирования. Код пока не подключён к API и интерфейсу; существующий сервер продолжает использовать старую схему. Перенос приложения и данных на PostgreSQL ещё не выполнен. Политика и согласие для записи требуют согласования. Тестовая PostgreSQL не подключена; проверка на реальной БД, миграция, UI и сквозной сценарий остаются необходимыми. Запрет изменять пром сохраняется.

## API (частично, без подключения к серверу)
Добавлен изолированный router для чтения свободных слотов и создания бронирований, настроек услуги и календаря, отмены записи. Защита административных методов и текст согласия передаются в router извне; без них создание router запрещено. Публичная форма получает версию согласия с сервера, а устаревшая версия отклоняется. 12 модульных и HTTP-тестов прошли; repository в тестах подменён, настоящая PostgreSQL и конкуренция запросов не проверены. Маршруты намеренно не подключены к старому серверу: у него SQLite-зависимая авторизация и отсутствует единая мигрированная PostgreSQL база. Тестовый DATABASE_URL в рабочем окружении есть, но его назначение и изоляция от пользовательских данных не подтверждены, поэтому подключение/изменение схемы не выполнялось. UI и перенос существующей очереди остаются незавершёнными; текст согласия для записи ещё не утверждён.

## Интерфейс записи (частично)
Добавлены React-страница `/booking/:publicId` и панель настроек в справочнике услуг: расписание по дням, исключения, посты, поля, ссылка и iframe, календарь и отмена. Интерфейс обращается к подготовленным маршрутам `/api/booking`, но эти маршруты всё ещё не включены в существующем сервере; приложение с ними сквозным образом не проверено. Реализация требует миграции существующей очереди на PostgreSQL, подключения репозитория к той же БД и корректной настройки серверных заголовков для встраивания. Страница отказывается отправлять данные, если сервер не предоставил текст и ссылки на документы; маршрутизатор не запускается без версии, текста и безопасных адресов обоих документов. Существующие `/privacy` и `/consent` описывают электронную очередь и не утверждены для записи; не считать их юридически пригодными без проверки. UI календаря показывает только интервалы текущего расписания и не показывает записи вне него после изменения расписания — требуется доработать. Vite build и 13 серверных модульных/HTTP тестов прошли; тесты используют mock, реальная PostgreSQL, конкурентность, UI и сквозной сценарий не проверены.

## Уточнение календаря и iframe
Календарь дополнен отдельным списком всех активных записей на выбранную дату, в том числе не пересекающихся с текущим расписанием; при изменении даты прежний результат скрывается. Для страницы `/booking/<uuid>` подготовлено исключение из запрета встраивания: только GET/HEAD на эту страницу допускает сторонние iframe, остальные страницы сохраняют SAMEORIGIN и frame-ancestors self. На прокси и в реальном браузере iframe не проверен. Серверные тесты заголовков и существующие тесты — 14 успешных; сборка интерфейса успешна. PostgreSQL и маршруты записи по-прежнему не подключены, сквозная проверка невозможна, пром не изменён.

## Дополнительная проверка настроек
Исправлена проверка пересечений графика: исключения больше не могут скрыть ошибки в проверочных датах. Пустой часовой пояс теперь запрещён; добавлено ограничение числа полей формы. 17 серверных тестов прошли с тестовыми подменами. Настоящая PostgreSQL и интеграция с существующим сервером не проверены, маршруты по-прежнему не подключены.

## Интеграционный тест PostgreSQL
Добавлен opt-in тест `server/tests/booking-postgres.integration.test.js` с отдельной случайной схемой: одновременные запросы на один пост, сохранение согласия, стабильность ID при выключении и повторном включении и отмена записи. Тест создаёт и удаляет собственную схему и запускается только при наличии `BOOKING_TEST_DATABASE_URL`; этот адрес должен указывать исключительно на изолированную непроизводственную БД. При запуске без переменной тест пропущен: 17 тестов прошли, 1 пропущен. Реальная PostgreSQL ещё не настроена, поэтому конкурентность в СУБД не подтверждена. Существующие маршруты, SQLite-зависимая очередь и данные пока не переведены.

## Безопасность тестирования и ошибок API
Интеграционный тест теперь требует явно заданного `BOOKING_TEST_ISOLATION_CONFIRMED=isolated-test-only` и имени тестовой базы с префиксом `test_`; эти проверки уменьшают риск случайного запуска, но не подтверждают изоляцию сервера сами по себе. Ошибки соединения и другие непредвиденные ошибки API возвращают общий ответ без внутренних сообщений; проверяемые ошибки ввода по-прежнему сообщаются пользователю. 20 тестов прошли, интеграционный тест PostgreSQL пропущен, реальная БД по-прежнему не проверена. Маршруты записи не подключены.

## Подготовка PostgreSQL на сервере
С согласия пользователя на подготовительные работы установлена PostgreSQL 16 отдельной службой на существующую VM. Слушает только localhost IPv4/IPv6, служба очереди во время установки оставалась активной (NRestarts=0); текущая база и настройки приложения не переключались. На сервере создана временная тестовая БД и роль с ограниченными правами, использован SSH-туннель; интеграционный тест на настоящей PostgreSQL прошёл: конкурентное занятие слота, согласие, выключение и повторное включение, отмена. Тестовую БД и роль после проверки удалили, отсутствие проверено. Это не проверка миграции очереди или сквозного UI. Подготовка не означает согласия на остановку сервиса: финальное переключение только после отдельно согласованного технического окна.

## Флаг интерфейса записи
Добавлен флаг сборки `VITE_BOOKING_ENABLED=true`: без него кнопка «Запись» в услугах неактивна и публичная страница показывает сообщение о недоступности. Это только ограничение интерфейса; при подключении маршрутов потребуется независимый серверный флаг, по умолчанию выключенный. Текущий API записи не подключён. Сборка Vite прошла, вид публичного маршрута с выключенным флагом проверен снимком; нажатие кнопки админки в пользовательском сценарии не проверено. На прод новая версия не выкладывалась. 20 серверных тестов прошли, тест настоящей PostgreSQL в этом запуске пропущен.

## Серверное отключение записи
В действующую SQLite-версию в песочнице добавлен шлюз `/api/booking`, всегда отвечающий 503 при выключенном модуле; запросы больше не проваливаются в HTML SPA. Для будущего PostgreSQL-приложения шлюз допускает включение только при явном предоставлении маршрутизатора. В этой SQLite-версии переключатель окружения для включения отсутствует намеренно: смешивать SQLite-очередь с отдельной PostgreSQL записи до миграции нельзя. Проверены GET, POST, PUT и отсутствие вызовов отключённого обработчика, а также отказ включения без него. Всего 23 теста прошли, интеграционный тест PostgreSQL в этом запуске пропущен. Промышленное приложение не обновлялось; SQLite → PostgreSQL, настройка согласия и сквозной сценарий остаются незавершёнными.

## Подготовка структуры для переноса очереди
Добавлен проект схемы PostgreSQL для восьми таблиц существующей очереди и read-only аудит исходной SQLite-схемы. Аудит явно останавливается при отсутствующих или неизвестных таблицах/столбцах, не выводит строки с персональными данными. Схема локальной копии `server/queue.db` соответствует ожидаемой; схема промышленной базы на этом этапе не проверялась. Даты намеренно представлены текстом для сохранения исходных значений, семантика запросов приложения на PostgreSQL ещё не проверена. Написаны тесты аудита: все 26 серверных тестов прошли, один интеграционный тест PostgreSQL пропущен. Это не перенос данных, не проверка резервной копии и не готовая миграция; схема PostgreSQL пока не применялась. Промышленная служба и база не изменялись.

## Проверка PostgreSQL-схемы и промышленной структуры
Структура восьми таблиц действующей базы прочитана без изменений и без извлечения строк: имена таблиц и столбцов совпадают с ожидаемыми аудитом. Во временной изолированной PostgreSQL-базе на сервере применена подготовленная схема, проверены состав столбцов, внешние ключи, синхронизация последовательностей после вставки ID и совместимость схемы с репозиторием записи. Полный запуск: 28 тестов прошли, в том числе два интеграционных PostgreSQL. Тестовые база и роль удалены, отсутствие проверено. Текущая служба очереди активна, счётчик перезапусков 0. Это не перенос строк, не проверка целостности данных и не готовность к переключению: код очереди остаётся SQLite-зависимым.

## Пробный импорт синтетических данных
Добавлена функция пробного импорта в пустую PostgreSQL-схему, с проверкой исходной схемы, транзакцией, проверкой количества строк и установкой последовательностей. Она предназначена только для репетиции с согласованным read-only снимком, не вызывается приложением и не является готовым инструментом миграции: необходимо обеспечить согласованный снимок, сверку содержимого всех полей, проверку ограничений и регрессию приложения. Проверены на PostgreSQL синтетические строки, внешний ключ, следующий ID, отказ от непустой схемы и откат при ошибке. Все 29 тестов прошли; временные БД и роль удалены. Реальные данные не переносились; служба очереди активна и не перезапускалась.

## Сверка содержимого пробного импорта
Пробный импорт дополнен сравнением каждого поля каждой исходной строки с PostgreSQL по первичному ключу до COMMIT, без вывода содержимого. Искусственное искажение значения при неизменном количестве строк приводит к ошибке и откату; затем синтетический импорт проходит. Повторно выполнены все 29 тестов на временной PostgreSQL-базе, включая тест искажения. Данный тест использует синтетический источник, не реальную копию SQLite: согласованный снимок, возможность восстановления, проверка реальных типов и полноценный перенос ещё не подтверждены.

## Чтение очереди из PostgreSQL
Создан отдельный асинхронный читатель текущего состояния очереди из PostgreSQL. На временной тестовой базе с синтетическими данными проверены текущий талон, сортировка ожидающих по приоритету, отбор по дате и отсутствие имени/телефона в публичной модели. Текущий контракт `field_values` сохранён для совместимости — возможное раскрытие персональных данных в этом поле требует отдельной проверки до запуска. Модуль не подключён к серверу: маршруты, Socket.IO и операции изменения очереди по-прежнему зависят от SQLite. Полный набор 30 тестов прошёл, включая тесты PostgreSQL; рабочая база не переключалась.

## Вызов талона в PostgreSQL
Добавлен отдельный неподключённый модуль вызова следующего и конкретного талона. Операции на день сериализуются транзакционной advisory-блокировкой; вызов отсутствующего конкретного талона не закрывает текущий. Проверены синтетические данные, два одновременных вызова одного талона, переходы состояний и пустая очередь на настоящей временной PostgreSQL. 31 тест прошёл. Для гарантии конкурентности все остальные будущие операции, меняющие очередь, должны использовать ту же блокировку; остальные маршруты и Socket.IO пока не адаптированы и модуль не подключён. Тест не подтверждает работу интерфейса или готовность к переключению.

## Завершение и возврат текущего талона
Неподключённый модуль PostgreSQL дополнен транзакционными операциями завершения текущего талона с причиной и возврата текущего талона в ожидание, с той же блокировкой на день, что и вызов. Тесты проверяют возврат, повторный вызов, завершение, сохранение причины и пустую очередь. Все 31 тест прошли на синтетических данных и временной базе PostgreSQL. Остальные операции, подключение к API и сквозная регрессия очереди ещё не выполнены.

## Дополнительные действия очереди PostgreSQL
В изолированном модуле добавлены возврат конкретного талона, возврат всех обслуженных и вызванных талонов и сброс очереди с сохранением последнего ID в настройках. Операции сериализованы по дню и проверены на временной PostgreSQL; все 31 тест прошли. Модуль всё ещё не подключён к API; незавершены адаптация остальных маршрутов, Socket.IO и сквозное тестирование. Переключение промышленной базы и включение записи не выполнялись.

## Маршруты очереди PostgreSQL
Подготовлен отдельный маршрутизатор очереди PostgreSQL с внедряемыми авторизацией, состоянием, действиями, оповещениями и журналированием. Он не подключён к текущему SQLite-серверу. ## HTTP-проверка очереди с PostgreSQL
Новый интеграционный тест запускает изолированное Express-приложение с настоящими маршрутизатором, состоянием и действиями PostgreSQL, но с тестовой авторизацией и заглушками оповещений и журнала. Проверены отказ без авторизации, приоритетный вызов, возврат, вызов конкретного талона, завершение, массовый возврат и сброс на синтетических данных. Все 33 теста прошли на отдельной временной БД. Действующий сервер, реальные авторизация и Socket.IO ещё не подключены и не проверены в этом сценарии.

## Адаптер уведомлений и журнала PostgreSQL
Добавлен отдельный неподключённый адаптер Socket.IO и журнала действий PostgreSQL. Unit-тест с заглушками проверяет отправку полного состояния администраторам, публичного — остальным и параметры записи журнала. Последний локальный запуск: 28 тестов прошли, 6 интеграционных PostgreSQL пропущены без тестовой базы. Реальные Socket.IO, журнал и авторизация совместно не проверены. Событие ticket:called сохраняет прежний контракт передачи полного талона всем подключённым клиентам — возможное раскрытие персональных данных необходимо исследовать и устранить с учётом совместимости до запуска. Также ошибка журнала/уведомления после фиксации транзакции может привести к ошибочному HTTP-ответу при уже изменённой очереди; это нужно исправить до интеграции.

## Ограничение данных события вызова
В неподключённом PostgreSQL-адаптере событие `ticket:called` теперь отправляет полный талон только в комнату администраторов, а остальным — идентификатор, номер, название услуги, статус и время вызова. ## Сбои после изменения очереди
В неподключённом маршрутизаторе операции, уже зафиксированные в БД, возвращают предупреждение вместо ложного HTTP 500 при сбое журнала, уведомления или повторного чтения состояния. Тест с заглушками воспроизводит все три сбоя после вызова и проверяет однократное выполнение операции и предупреждение. 29 тестов прошли, 6 PostgreSQL-интеграционных пропущены без тестовой БД. Предупреждение ещё не обработано интерфейсом, надёжная транзакционная запись аудита и проверка реальных ошибок PostgreSQL/Socket.IO остаются необходимыми; сбой COMMIT остаётся неоднозначным. Изменение не подключено к промышленному серверу.

## Рабочее превью модуля записи в песочнице

Для записи поднят отдельный процесс `server/preview/bookingPreviewServer.js` (порт 6621): он обслуживает только `/api/booking`, использует настоящий репозиторий записи на PostgreSQL и тот же секрет JWT, что и песочницевый вход администратора, поэтому отдельный вход не требуется. ## Календарь дат в виджете
Виджет перестроен в три шага: календарь месяца → слоты выбранного дня → поля клиента и кнопка «Записаться». В календаре зелёным отмечены дни, где есть свободные места, красным — дни без записи: прошедшие даты, нерабочие дни по расписанию, дни с полностью занятыми слотами. Причина недоступности дня видна в подсказке. Слоты дня окрашены так же: зелёные доступны, красные заняты; выбранный слот выделяется синим. Поля клиента и блок согласия появляются после выбора слота.

Добавлен публичный маршрут `GET /api/booking/public/:publicId/month?month=YYYY-MM`, который отдаёт за месяц агрегированную доступность по дням: дата, признак доступности, причина и число свободных мест. Данные клиентов через этот маршрут не передаются; причина недоступности (`past`, `closed`, `full`) и месяц считаются на сервере в часовом поясе услуги, поэтому клиент не может получить чужие данные или подделать расписание. Без параметра `month` сервер отдаёт текущий месяц услуги; некорректный месяц отклоняется с 400.

Ссылка виджета теперь понимает параметры `?month=ГГГГ-ММ`, `?date=ГГГГ-ММ-ДД` и `?time=ЧЧ:ММ` — они открывают календарь на нужном месяце, сразу выбирают день и отмечают слот. Это же позволяет проверять виджет по прямой ссылке.

Проверено на локальной PostgreSQL песочницы: месяц с рабочими, выходными и полностью занятым днём, прошедшие дни текущего месяца, выбор даты и слота, появление полей и кнопки, отказ на некорректный месяц. Добавлены 8 тестов маршрута и один интеграционный тест PostgreSQL; полный набор — 43 из 43 пройдено. Промышленный сервер не изменён, запись на проме не включалась.

## Вкладка «Запись» в панели администратора
Рядом со вкладкой «Очередь» появилась вкладка «Запись». Она открывается по адресу `/admin?tab=booking`, видна только пользователям с ролью администратора (оператору вкладка не показывается, сервер всё равно отвечает 403).

Вкладка показывает календарь месяца по выбранной услуге: в каждом дне видно число записей и число свободных мест из общего количества постов. Цвет ячейки: зелёный — есть свободные места, жёлтый — есть записи, серый — запись по расписанию не ведётся. Отмена сразу обновляет и список слотов, и счётчики месяца.

Проверено на локальной PostgreSQL песочницы: календарь показывает 30 дней месяца, день с записями помечен, по клику открываются слоты с данными клиентов («Номер авто», «Телефон»), отмена записи убирает её из панели и из счётчиков месяца. ### Выбор канала услуги
У каждой услуги два независимых канала: «Очередь» (живая электронная очередь) и «Запись» (предварительная запись). Каналы включаются и выключаются отдельно, поэтому услуга может существовать только в записи, только в очереди или в обоих каналах сразу.

Как это сделать:
- **При создании услуги** в форме есть блок «Каналы» с чекбоксами «Очередь» и «Запись». По умолчанию включена очередь; чтобы создать услугу только для записи, снимите «Очередь» и отметьте «Запись». Пустой выбор не принимается: хотя бы один канал должен остаться включённым.
- **В справочнике услуг** у каждой строки две метки каналов: «Очередь» (Активна/Отключена) и «Запись» (Включена/Выключена). Метку можно переключить прямо в таблице; кнопка «Параметры» открывает расписание, постоянную ссылку и код виджета.
- Услуга с выключенным каналом «Очередь» не показывается посетителям в очереди, но остаётся в справочнике администратора, доступна для записи и в календаре «Запись».
- При первом включении канала «Запись» услуга получает постоянный UUID виджета и настройки по умолчанию (пн–пт 09:00–18:00, 30 минут, вместимость 1) — их нужно уточнить в «Параметрах». При выключении и повторном включении UUID, расписание и поля сохраняются.

Серверная часть: `POST /api/services` и `PUT /api/services/:id` принимают поле `enabled` (канал «Очередь»); состояние канала «Запись» хранится в таблице `booking_config` и отдаётся административным маршрутом `GET /api/booking/services` (только для администратора). Переключение канала «Запись» не трогает расписание и постоянную ссылку.

В песочнице справочник услуг лежит в SQLite, а данные записи — в PostgreSQL, поэтому сервер записи зеркалит строки услуг в свою базу перед обработкой запроса. В целевом приложении обе таблицы будут в одной базе PostgreSQL, и это зеркалирование не понадобится.

Проверено на песочнице: услуга «Диагностика подвески» создана только с каналом «Запись» — в живой очереди посетителей её нет, в справочнике администратора она есть, канал «Запись» включается и выключается из таблицы, виджет отдаёт слоты, запись через виджет создаётся (201) и видна в календаре администратора. Сквозная проверка интерфейса: `client/scripts/check-service-channels.mjs`.

### Управление услугами: единое окно редактирования
Вкладка «Услуги» (шестерёнка в шапке → «Услуги») перестроена по решению владельца сервиса:

- Сверху — заголовок «Услуги» и кнопка «Добавить услугу». Ниже — список услуг в виде таблицы: название с описанием, состояние каналов («Очередь: вкл/выкл», «Запись: вкл/выкл» — переключаются прямо в строке), среднее время, приоритет, лимит талонов в день, отметка «по умолчанию» и действия «Редактировать» и удаление.
- Кнопка «Редактировать» открывает модальное окно со всеми настройками услуги — и очереди, и записи. Отдельная форма создания услуги и отдельное окно «Параметры записи» больше не нужны.
- Модальное окно устроено так: сверху карточки каналов «Очередь» и «Запись» с галочками (нужно оставить хотя бы один канал, иначе услуга не работает), ниже вкладки «Основное», «Очередь», «Запись» (вкладки показываются только для включённых каналов), внизу кнопки «Закрыть» и «Сохранить».
  - «Основное»: название, описание, отметка «Сделать услугой по умолчанию».
  - «Очередь»: среднее время, приоритет, лимит талонов в день и редактор полей анкеты (те поля, которые клиент заполняет при получении талона).
  - «Запись»: длительность приёма, количество постов, часовой пояс, рабочие дни и часы, нерабочие даты, поля клиента, постоянный виджет (ссылка, кнопки «Открыть виджет» и «Скопировать ссылку», код iframe).
- Состояние канала «Запись» в окне берётся из серверной настройки услуги, поэтому окно не может случайно выключить уже настроенный канал. Расписание и постоянная ссылка сохраняются при выключении и повторном включении записи.
- Если канал «Запись» выключен, а настройки уже создавались, они не теряются: при сохранении сервер получает прежнее расписание с выключенным каналом, поэтому постоянная ссылка продолжает работать.

Код: `client/src/components/admin/ServicesTab.jsx` (список и кнопка), `client/src/components/admin/ServiceEditorModal.jsx` (модальное окно со вкладками), `client/src/components/admin/QueueFieldsEditor.jsx` (поля анкеты очереди). Прежний отдельный компонент `BookingSettings.jsx` удалён.

Проверено: `client/scripts/check-service-channels.mjs` — кнопка «Добавить услугу» есть, у каждой услуги два независимых канала, переключение канала «Запись» не меняет расписание, модальное окно открывается, в нём есть галочки обоих каналов, вкладки «Очередь» и «Запись», постоянная ссылка и кнопка «Открыть виджет»; состояние канала проверка восстанавливает.
